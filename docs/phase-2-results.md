# Phase 2 — First Home and Developer Preview

Implementation, screenshots and validation of the existing Foundations application. All pictured progress is synthetic. Application source: `c4b6f27b1dd77d6c6a357e6eed704c81be890823`. GitHub Actions and Pages deployment succeeded; verification and evidence follow below.

## What changed

Genuinely new version 2 profiles begin on the original residential lot with grass, road, sidewalks, trees, modest planting and property markers. The first valid recorded habit completion permanently unlocks **Your First Home**. It uses the existing completion transaction and qualifies independently of stars, including a zero-star completion at the daily cap. No scoring values, later thresholds or project IDs change.

The welcome sheet previews Classic Cottage, Modern Craftsman and Traditional Brick in the existing Three.js world. Confirming saves the chosen home before the 2.8-second gentle reveal starts. Skip settles immediately, and reduced motion shows the completed home directly. Choosing later preserves the pending reward; reload during selection reopens it, while reload during construction shows the already saved house. The same selector provides free, reversible house changes from Your town.

Settings → Developer Preview → Enter Developer Preview opens a disposable town. A persistent badge and Exit identify the mode; controls collapse to leave the neighborhood visible. Six sections provide simulated stars, existing milestone jumps/all/empty/reset, three houses and visibility/construction, three existing backyards and visibility, four lighting moods/automatic time, camera coordinates/zoom/rotation/reset, and five test scenarios. No new city projects, models, habit systems, tracking, backend or cars are added.

The same procedural homes, gardens, backyard assets, continuous world, local-time lighting, camera gestures and responsive habit tracker remain in place. The home stays anchored at world(-5,.13,-4.6). Only its existing meshes are batched separately to permit a short reveal.

## Save migration and isolation

The existing `foundations.v1` storage key stays in use, with JSON schema version 2 and an explicit `onboarding.firstHomeUnlocked` flag. All valid version 1 profiles are treated as existing homeowners, including zero-star users. All validated habits, schedules, completion snapshots, construction selections and unknown fields survive load/import. The exact stored version 1 bytes are archived once under `foundations.pre-v2` before overwriting; Settings exposes that backup. A failed archive leaves original storage untouched. Malformed and unsupported saves remain protected rather than silently replaced.

Eligibility is committed with the completion. A confirmed first house requires a successful durable write before the UI starts animation. Failure leaves selection pending with a visible error; browser closure never needs animation completion to retain the home. Web Locks serialize supported browsers' real transactions, including startup creation/migration; only the first confirming writer receives the first-construction response.

The store has separate real and preview signals. Entry deep-clones genuine state; preview star totals are disposable metadata outside reward history. Preview commands and normal command APIs target that copy while active, with no localStorage/IndexedDB/session flag or synchronization writes. Exports always read the real signal; real backup import is blocked in preview. Genuine storage events continue updating the real signal behind the preview, so exit restores current real progress rather than an obsolete snapshot. Reload reads real storage and discards preview. Session epochs invalidate delayed camera events and queued actions across mode/scenario transitions.

Developer Preview is deliberately available through Settings in production. It is a client-side tool, not a security boundary.

## Review and implementation decisions

One independent read-only whole-change review found a scenario-transition bug: an old construction request could replay after a preview reset/jump and replace its overview camera with Home. Two failing regressions exercised the actual App effect and Town input synchronizer. The fix clears old construction status and consumes the previous request across session changes; a new request within the same session still works. The resulting full unit suite was 81/81 PASS. No additional material code findings were reported; no second reviewer was dispatched.

| Decision                                                        | Reason and tradeoff                                                                                                                                                                |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preserve every valid v1 homeowner, including zero-star profiles | Prevents loss of visible construction; legacy users deliberately bypass the new-player sequence.                                                                                   |
| Separate real and disposable preview signals                    | Prevents rollback/export/tab leakage; preview work is intentionally discarded on reload.                                                                                           |
| Batch the home separately inside the existing world             | Enables its reveal without replacing the renderer; modest extra material draw calls remain to measure on phones.                                                                   |
| Treat a constructed home as already offered in its session      | Deliberately hiding a preview house no longer reopens onboarding; a fresh pending/scenario session can still offer selection.                                                      |
| Cache shadows during the small reveal                           | Keeps the short animation lighter; the transient shadow is approximate until final settlement.                                                                                     |
| Strengthen other-tab validation                                 | Actual preview-tab backup export and visible genuine stars after exit complement the storage-event unit test; shared-storage assertions alone do not prove the visible real state. |
| Exercise a failed durable save through reload                   | Synthetic quota injection verifies the pending reward, error and no celebration; unit tests separately preserve original bytes.                                                    |
| Serialize startup creation and migration                        | A concurrent completion can no longer be replaced by a stale constructor snapshot; browsers without Web Locks retain the documented single-tab limitation.                         |
| Report background/GPU/Safari evidence limits                    | Elapsed-time settlement and reload tests protect saved progress, but do not certify real browser background throttling or physical-device timing.                                  |

Before publication, the author also reproduced a startup race: constructor migration could overwrite a newer completion while bypassing the shared Web Lock. The publication run 39073734269 was cancelled before deployment. Three failing unit cases and an actual held-lock two-tab browser case now pass after startup was routed through the same fresh-state transaction as genuine actions. That fix passed84unit and33onboarding/preview cases; final85unit and87browser results above include the later rendering improvement. This additional fix was necessary to satisfy the owner's explicit save-integrity requirement; it was not deferred to preserve a one-pass review preference.

The archived cancelled CI runs also revealed 30-second timeouts in the monolithic 9-combination legacy test and several desktop workflows. The matrix is now three independent house cases, retaining all nine combinations and assertions. A failing renderer regression demonstrated that identical lighting preferences repainted the town on every camera/history synchronization; the redundant draw is now skipped. World replacement and clock changes still apply lighting. No timeout was increased and no visual detail or test assertion was removed. CI now reports every test rather than buffering progress dots.

No minor code findings were deferred. Follow-up device/performance checks below remain explicit validation limits.

## Performance and architectural limits

The 34 local captures at `c4b6f27` passed all scripted checks: no horizontal overflow, console/page/WebGL errors or lost contexts, no external request hosts, and byte-identical genuine storage during preview and after exit. The author inspected empty-lot, all three house previews, construction, completed-home and developer controls in portrait, compact portrait, landscape and desktop. Short sheets scroll vertically; compact portrait deliberately retains city space rather than fitting every action above the fold.

The hosted capture pass adds22 screenshots from fresh synthetic profiles at the deployed Pages URL in portrait and landscape. All21 deployed browser tests passed. The page returned HTTP200, used `<base href="/foundations/">`, loaded the production module with HTTP200, and its SHA256 (`9f9661545d3797954307ef9ee77c11e6a254ef910ceb8357d4970d13f36c4264`) matched the final local build. Requests observed during hosted capture went only to `haydenmay.github.io`. Both hosted idle samples recorded zero renders over700ms; the first-home durable write completed before the reveal started. See [host verification](evidence/phase-2/hosted-verification.json), [hosted tests](evidence/phase-2/hosted-browser.txt), and [hosted metrics](evidence/phase-2/hosted/metrics.json).

Rendering remains event-driven when idle. All four 700 ms idle samples recorded **zero renders** after construction. The empty lot uses 21 draw calls/80,678 triangles; the completed Cottage uses 76/186,792; Craftsman 87/185,132; the all-project daytime preview 125/237,662. These are rendering counts, not a mobile frame-rate claim. Construction is capped at 30 updates/second, but the Windows software-rendered captures showed coarse animation steps. Diagnostic render counts and automation elapsed times are not physical-phone FPS; cached measurement frames are marked separately from the last UI update, which can include shadow passes. Test real devices; if needed, add adaptive pixel ratio/shadow resolution or reduced-detail foliage within the current factories.

Construction now reuses cached shadows during its small rise/scale, refreshing at visibility changes and settlement; it avoids unchanged settled 3D frames while the short DOM accent finishes. This preserves responsiveness but gives the tiny transient rise an approximate shadow until settlement. Skip/disposal cancels the animation request and restores the house. Identical lighting settings no longer trigger redundant paints during camera/history synchronization. The existing pixel-ratio cap and one shadowed sun remain. No perpetual animation or expensive new effect is introduced.

The current 36×29 terrain, bounded camera and world-wide static material batches fit the existing eight projects. Future continuous-city growth should extend terrain/camera bounds and introduce spatial lot/chunk batches and level of detail. Home must continue targeting the original lot; no separate scenes or level map have been introduced.

Procedural art retains the previous visual compromises against the approved boards: simpler leaf sprays, repeating surface maps, approximate shadows/reflections, no offline global illumination or photographic depth of field. The inspected starting-lot and completed-home captures preserve the previous detailed miniature appearance. Optimized authored models and foliage atlases can later replace the existing asset factories.

Browser-local storage can be cleared or blocked. Keep private JSON backups; storage failure permits in-tab habit tracking but blocks an unsaved first-home confirmation. Old tabs should be closed after upgrade. Older browsers without Web Locks cannot guarantee simultaneous real writes; use one tab there. Physical iOS/Android, actual Safari, screen-reader and low-memory hardware checks are not performed by Chromium viewport emulation and remain necessary follow-up work.

Recommended next work is owner review of the welcome/preview experience, followed by physical Safari/iOS and Android checks. No neighborhood expansion is part of this delivery.
